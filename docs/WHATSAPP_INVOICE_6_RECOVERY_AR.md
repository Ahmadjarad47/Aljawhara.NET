# إصلاح فاتورة WhatsApp رقم 6 للطلب 48

تاريخ التنفيذ: 21 أكتوبر 2026. نُفّذ الاختبار على خادم المشروع Ubuntu 22.04.5 LTS، بحساب الخدمة `www-data`، قبل إعادة الفاتورة إلى الإرسال.

## النتيجة

- قبل الإصلاح: `Failed (7)`، و`AttemptCount=5`، و`INVOICE_PREPARATION_FAILED`.
- نجح PDF اصطناعي من 3 منتجات في صفحة واحدة، ومن 60 منتجاً بأسماء عربية طويلة في 6 صفحات، وكذلك حالة صفر منتجات.
- نجح PDF الحقيقي للفاتورة 6 باستخدام إعدادات الخدمة نفسها: **272,206 بايت**، ومنتج واحد، دون تغيير حالة الفاتورة أثناء الاختبار.
- بعد إعلان نتائج PDF، نُفذ Retry إداري للفاتورة **6 فقط** المرتبطة بالطلب **48**. وصلت إلى `Sent (4)` بعد محاولة واحدة، مع وجود `ProviderMessageId` و`WhatsAppMessageId`. هذه الحالة تثبت الإرسال؛ لا تُعتبر إثبات تسليم أو قراءة.
- حُفظ سجل تدقيق واحد يحفظ المحاولات الخمس السابقة ورمز الخطأ وبصمة PDF وهوية الصيانة الإدارية. إعادة الطلب الإداري بنفس معرّف العملية لا تضيف محاولة أو سجل تدقيق جديداً.
- مقارنة بصمات بيانات الدفع والطلب قبل العملية وبعدها أثبتت عدم تغيرها. كذلك بقيت سجلات الفواتير 1–5 دون تغيير، في `Skipped`.

## الأسباب المثبتة والإصلاح

1. كان `PLAYWRIGHT_BROWSERS_PATH=/opt/aljawhara-playwright` مضبوطاً، لكن المجلد فارغ. ثُبت Chromium وتبعياته من CLI المرفق بحزمة `Microsoft.Playwright 1.58.0`، داخل المسار نفسه وبملكية `www-data`.
2. ملف `.playwright/node/linux-x64/node` المنشور كان بصلاحيات `0744`، فلا يستطيع `www-data` تنفيذه. أُعيد إنتاج `Win32Exception (13): Permission denied` في نسخة معزولة، ثم صُححت الصلاحيات إلى `0755`.
3. قناة `chromium` الكاملة احتاجت مجلدات إعدادات قابلة للكتابة. اختُبرت مشكلة تهيئة Crashpad وعولجت بتوفير `HOME` و`XDG_CONFIG_HOME` و`XDG_CACHE_HOME` داخل `/var/lib/aljawhara` بملكية الخدمة. أُعيد اختبار الفاتورة الحقيقية بعد نشر الإصلاح، بالبيئة الموروثة من الخدمة ومن دون تجاوز لمسار Node، ونجح.

أُضيفت إعدادات المسارات إلى `deploy/ubuntu/environment.conf` وسكربت `install-invoice-browser.sh`، وأصبح السكربت ضمن ملفات النشر وتستدعيه GitHub Actions قبل إعادة تشغيل الخدمة لتجنب تكرار فقد صلاحية التنفيذ.

## تسجيل الخطأ وحماية البيانات

يلتقط `WhatsAppInvoiceProcessor` الاستثناء ويستدعي `InvoiceFailureLog` عبر `ILogger`. يسجل رقم الفاتورة، ونوع الاستثناء الأصلي، و`HResult`، وأطر Stack Trace الأصلية، والاستثناءات الداخلية بما فيها AggregateException.

لا يُمرر كائن الاستثناء الخام إلى موفر السجلات؛ تُستبعد `Message` و`Data` ومسارات ملفات المصدر لأنها قد تحمل HTML أو بيانات عميل أو SQL أو روابط ورموز وصول. رمز قاعدة البيانات يبقى مختصراً، ولا تُنسخ بيانات العميل إلى سجل الخطأ أو سجل Retry.

## اختبار JavaScript وPDF

أثبت الاختبار الفعلي أن `EvaluateAsync` يعمل مع `JavaScriptEnabled=false`؛ لم يكن هذا الخيار سبب العطل. بقيت سكربتات المستند معطلة.

المسار المختبر يشمل تحميل الخط وانتظار `document.fonts.ready`، وقياس ارتفاع الصفوف، وإنشاء جداول مستقلة للصفحات، ونقل صفوف النهاية عند توفر المساحة، ثم التحقق من عدد الصفوف ووجود قسم إجمالي واحد وعدم تجاوز ارتفاع الصفحة. وُضعت مهلة لخطوات التقييم ومنع للموارد الخارجية عبر Offline وCSP وحجب الطلبات.

| البيانات الاصطناعية | الحجم بالبايت | الصفحات | النتيجة |
| --- | ---: | ---: | --- |
| صفر منتجات | 265813 | 1 | ناجح |
| 3 منتجات | 279315 | 1 | ناجح |
| 60 منتجاً بأسماء عربية ملتفة | 297504 | 6 | ناجح |

أكد استخراج النص وجود علامات المنتجات الستين مرة واحدة لكل منتج، ووجود `1482.400 KWD` في الصفحة الأخيرة. رُوجعت صور الصفحات الست بصرياً: العربية والشعار والرؤوس وترقيم الصفحات والإجمالي دون قص أو تداخل. شملت البيانات نصاً يشبه `<script>` للتحقق من عرضه كنص فقط.

لم يُصدر PDF العميل إلى ملفات الاختبار أو هذا التقرير. نماذج الاختبار وصورها اصطناعية فقط، ضمن `artifacts/whatsapp-recovery/pdf/`.

## Retry الإداري

المسار الجديد:

```http
POST /api/whatsapp/admin/invoices/6/retry-preparation
Authorization: Bearer <admin JWT>
Content-Type: application/json

{
  "expectedOrderId": 48,
  "requestId": "d706247e-671b-4388-a0f5-68bab2783594"
}
```

المعرّف أعلاه هو للعملية المكتملة؛ تكراره لا يرسل مجدداً. واجهة الإدارة تتطلب `AdminOnly` وهوية مستخدم. مسار الصيانة على الخادم استخدم **الخدمة نفسها** عبر أداة محددة للفاتورة 6 والطلب 48، من جلسة SSH الإدارية، وهوية التدقيق `Maintenance:SSH-root`؛ الأداة لا تحتوي مرسلاً أو اتصالاً ببوابة دفع.

قائمة السماح `PreparationRetryInvoiceIds` فارغة افتراضياً. إعداد الخادم يسمح بالرقم **6 فقط**، ولا توجد عملية تحديث جماعي أو إعادة تلقائية للفواتير الفاشلة الأخرى.

شروط الرفض قبل أي تحديث:

- حالة غير `Failed` أو سبب غير `INVOICE_PREPARATION_FAILED`، أو طلب غير مطابق.
- أي `ProviderMessageId` أو `WhatsAppMessageId`، حتى لو كان النص فارغاً، أو `DispatchStartedAtUtc` أو حدث تسليم أو دليل تسوية سابق.
- أي أثر إصدار رابط وسائط أو وجهة أو اسم تطبيق أو حجز عامل ما زال محفوظاً.
- حدث مزود غير مربوط على الوجهة والتطبيق منذ إنشاء الفاتورة؛ الرفض احترازي حتى لا تُعتبر نتيجة مجهولة آمنة.
- دفع أو معاملة غير Paid، أو استرداد، أو COD، أو دليل تحقق غير مكتمل، أو مبالغ/عملة غير مطابقة، أو حالة طلب غير مؤهلة.
- موافقة غير موجودة أو غير مطابقة للهاتف أو إلغاء موافقة لاحق، أو وجهة Sandbox غير مسموحة.
- فشل توليد PDF، أو وجود سجل Retry سابق للفاتورة.

تعمل القراءة والتحقق وتوليد PDF والتحديث وسجل التدقيق داخل معاملة `Serializable`. يُعاد فحص شروط عدم الإرسال و`RowVersion` عند التحديث الذري. القيدان الفريدان على `InvoiceId` و`RequestId` يمنعان التكرار، ويُعالج تعارض الطلبات دون منح محاولة إضافية. يظل سجل المحاولات السابق محفوظاً في التدقيق قبل بدء عداد المحاولة الإدارية الجديدة من صفر. يستخدم العامل ملف PDF الذي اختُبر وحُفظ في المعاملة نفسها، ثم يعيد فحص الدفع والموافقة وفق المنطق القائم.

لم يتغير منطق Sadad أو اعتماد Paid أو الحالات المالية أو تصنيف نتائج Gupshup المجهولة. كل فاتورة بدأت Dispatch سابقاً تبقى خارج مسار Retry الجديد.

## التحقق والنشر

- **65 اختباراً ناجحاً** لمسار واتساب وRetry والأخطاء والصلاحيات، تشمل طلبات متزامنة، تكرار الطلب، ورفض آثار Dispatch والموافقة غير الصالحة وفشل PDF.
- **56 اختباراً ناجحاً** إضافياً للدفع وSadad والموافقات والترحيلات.
- Build ناجح. توجد تحذيرات Nullable سابقة في ملفات البريد والمصادقة والمستودعات.
- لا اختلاف بين نموذج EF وآخر Migration.
- الترحيل `20261021133301_WhatsAppPreparationRetryAudit` أضاف جدول التدقيق وقيديه فقط. طُبق بدور مالك جداول التطبيق قبل نشر الملفات.
- نُسخت ملفات التطبيق السابقة إلى مجلد احتياطي مقيد على الخادم، ثم نُشرت التجميعات المحدثة وأُعيد تشغيل الخدمة. لم تُستبدل إعدادات الدفع أو الأسرار.
- الخدمة `active` بعد الإصلاح. توجد نسخة إعداد الخدمة الجديدة في `95-invoice-browser.conf`.
- فحص HTTP بعد النشر: `/health` أعاد `200`، ومسار Retry دون مصادقة أعاد `401`.
- تكرار معرّف عملية الاستعادة على الخادم أعاد `REQUEST_ALREADY_RECORDED`، وبقيت محاولة الإرسال واحدة وسجل التدقيق واحداً.
- تغييرات المصدر محفوظة محلياً دون commit أو push؛ إصلاح الخادم نُشر مباشرة. تعديل خط النشر في المستودع يصبح فعالاً عند رفعه إلى Git.

نتائج الاختبارات المحلية:

أداة الاختبار القابلة لإعادة التشغيل دون قاعدة بيانات أو إرسال:

```bash
dotnet publish tools/Ecom.InvoicePdfSmoke -c Release -r linux-x64 --self-contained false -o /path/to/smoke
cd /path/to/smoke
sudo -u www-data env PLAYWRIGHT_BROWSERS_PATH=/opt/aljawhara-playwright \
  HOME=/var/lib/aljawhara XDG_CONFIG_HOME=/var/lib/aljawhara/.config \
  XDG_CACHE_HOME=/var/lib/aljawhara/.cache \
  dotnet Ecom.InvoicePdfSmoke.dll /tmp/invoice-pdf-smoke
```

يجب أن تكون ملفات النشر مقروءة، وملف Node قابلاً للتنفيذ، وأن تكون نسخة Chromium مطابقة لحزمة Playwright. راجع [توثيق المتصفحات الرسمي](https://playwright.dev/dotnet/docs/browsers).
