# تقرير تنفيذ المرحلة الثانية — الدفع والاسترداد بدرجة إنتاجية

التاريخ: 2026-10-18  
القرار النهائي: **NO-GO للإنتاج** إلى أن يكتمل عقد التحقق الرسمي من Sadad واختباره اعتمادياً.

## ما نُفّذ فعلياً

أصبح إنشاء الطلب عملية محلية ذرّية واحدة تشمل الطلب والعناصر والمعاملة ومحاولة الدفع وحجوزات المخزون/الكوبون ورسائل Outbox. لم يعد مسار checkout يستدعي Sadad بعد commit مباشرة، ولا توجد معاملة SQL مفتوحة أثناء HTTP. أزيل قفل `ConcurrentDictionary` المحلي؛ الحماية الآن بفهرس SQL فريد، انتقالات مشروطة، وlease دائم يصلح لعدة نسخ.

أضيفت كيانات `PaymentAttempt`, `InventoryReservation`, `CouponReservation`, `OutboxMessage`, `PaymentTransitionAudit`, و`OrderNumberCounter`. لكل محاولة دفع مفتاح مستقل ومرجع تاجر ثابت، ولا يُستخدم `OrderId` كهوية وحيدة. حالات النتائج البعيدة غير المؤكدة تتوقف في `RequiresReconciliation` من دون إعادة إرسال عمياء أو تعليم الطلب مدفوعاً.

أصبح `Idempotency-Key` مدعوماً في checkout: الطلب المكافئ يعيد العملية نفسها، وتغيير الحمولة بالمفتاح نفسه يعيد 409. بقي الرأس اختيارياً لتوافق العملاء القدامى، لكن retry الآمن يتطلبه. استعادة guest token للطلب ذي المفتاح تستخدم HMAC ومفتاح نشر ثابت، بينما لا يُخزّن السر الخام.

أضيفت حالة تهيئة صريحة إلى استجابة checkout، وواجهة `GET /api/orders/{id}/payment-status` لاسترجاع الرابط الموجود/الحالة بنفس صلاحية المستخدم أو capability الخاصة بالضيف. أُغلقت نقاط الإدارة القديمة التي تنشئ/تعالج دفعة مباشرة بـ410 حتى لا تتجاوز المنظومة الجديدة.

## المال والمخزون والتزامن

وُسّعت حقول المال في المنتج والمتغير والطلب والعنصر والمعاملة والاسترداد والكوبون وCarousel إلى `decimal(18,3)`. سياسة التقريب موحّدة: ثلاث خانات و`MidpointRounding.AwayFromZero`. أثبت LocalDB حفظ واسترجاع `12.345 KWD`. الترحيل لا يخترع دقة فُقدت سابقاً؛ rollback إلى خانتين قد يقرّب البيانات ولذلك يحتاج نسخة احتياطية ونافذة صيانة.

الدفع الإلكتروني يحجز المخزون 30 دقيقة. الدفع الموثق يؤكد الحجز، والإلغاء/الانتهاء يعيده مرة واحدة. الدفع المتأخر بعد التحرير يتحول إلى reconciliation ولا يبدأ fulfilment. سياسة COD صريحة: يثبت المخزون عند checkout، ويبقى Transaction Pending حتى التحصيل، ويُعاد مرة واحدة عند إلغاء مسموح.

استخدام الكوبون يُحجز بتحديث SQL شرطي يمنع تجاوز الحد الأخير، ثم يؤكد أو يحرر مع الحجز. أرقام الطلبات تستخدم عداداً يومياً ذرياً بـ`MERGE ... WITH (HOLDLOCK)` مع الحفاظ على `ORD-yyyyMMdd-NNNN`.

## Outbox والبريد

أزيل `Task.Run` من المتحكم. إشعار الطلب يُحفظ داخل معاملة checkout، ويعالجه worker بنطاق DI جديد، lease، backoff، حد محاولات وDeadLetter. فشل البريد لا يغيّر حالة الدفع. مفتاح dedup يمنع إنشاء إشعار أعمال ثان للعملية نفسها، مع بقاء طبيعة SMTP نفسها at-least-once عند انقطاع الإقرار بعد الإرسال.

## نتيجة الاختبارات والثوابت المثبتة

النتيجة الأخيرة: **68 ناجح، 0 فاشل، 0 متخطى** على LocalDB مع Sadad mock. شملت 50 طلباً متزامناً بالمفتاح نفسه موزعة على مضيفي API، retry دفع بمفتاح مستقل، عاملين على الرسالة نفسها، stock=1، الحد الأخير للكوبون، تعطل العامل، timeout مجهول، عدم إعادة الإرسال، انتهاء الحجز، دفعاً متأخراً، finalization مكرراً، COD، واسترداد البريد بعد فشل.

الثوابت المثبتة: لا مخزون سالب؛ لا استعادة مزدوجة؛ لا تجاوز لحد الكوبون؛ مفتاح checkout لا ينتج عمليتين؛ المفتاح مع حمولة أخرى مرفوض؛ المرجع والفاتورة وOutbox event فريدة؛ `Paid` الإلكتروني يتطلب evidence موثوقاً ومبلغ/عملة/فاتورة مطابقة وحجزاً فعالاً؛ `12.345` يبقى كما هو في SQL.

## المخاطر والمتطلبات المتبقية

Sadad لم يقدّم بعد حقول الحالة النهائية والمبلغ والعملة وهوية التاجر والتوقيع/منع replay وضمان idempotency أو lookup بالمرجع. لذلك بقي webhook/callback مغلقاً بأمان، ولا ندعي exactly-once خارجياً. كما يلزم قبل النشر إعداد secrets الثابتة على كل النسخ، بريد الإدارة وSMTP، تشغيل preflight على نسخة بيانات، مراقبة DeadLetter/Reconciliation، واختبار staging مع مزود الدفع.

النتيجة: المعمارية المحلية والتزامن والاسترداد أصبحت جاهزة للاختبار الإنتاجي، لكن بوابة الدفع الإلكتروني الكاملة تبقى **NO-GO** حتى استلام عقد Sadad الرسمي وتنفيذ/اعتماد verification adapter. يمكن إبقاء COD فقط ضمن قرار نشر منفصل بعد إكمال قائمة التشغيل والأسرار.
