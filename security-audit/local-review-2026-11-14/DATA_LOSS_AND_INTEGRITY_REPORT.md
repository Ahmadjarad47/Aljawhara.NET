# Data loss and integrity

All writes used uniquely named disposable databases in a PostgreSQL 18 cluster on loopback. No existing application database was used. No data-loss invariant failed in the completed checks.

The selected PostgreSQL suite exercised rollback, three-decimal currency, stock and coupon contention, concurrency control for stale workers, duplicate checkout and order numbering, rollback of account changes, payment verification failure, expired dispatch leases, outbox retries, refund/status safeguards, shipping migrations, and actual `pg_dump` / `pg_restore`. It also tested retaining prior backups when a dump fails or a blocked dump is cancelled. The final isolated run passed 53 of 53 selected tests. Earlier runs hit missing process-level guest key and invalid Telegram fixture configuration before assertions could run; those were resolved for the final isolated run. A separate workspace run passed all 13 selected startup, image and export checks. See [selected test results](selected-test-results.json).

The four ordinary browser orders included one guest order and three customer orders. The [database snapshot](database-invariants.json) found zero item or transaction orphans, zero order/transaction amount mismatches, four ordered units, and eight remaining units from twelve. Four coupon reservations existed. These cash orders correctly had zero electronic payment attempts. The test suite, rather than the browser, exercised invoice dispatch and reconciliation with doubles.

An administrator was refused deletion of a category with a subcategory (400); the category and nested product stayed readable. A normal product delete returned 204, the public product returned 404, and order and transaction endpoints still returned 200. The [post-delete assertions](delete-invariants.json) recorded the soft-deleted product, four retained order items, one retained review and one retained transaction for the checked order.

The [live foreign-key inventory](database-delete-rules.txt) records the current migration's behavior for hard deletes. Catalog details, variants and ratings can cascade from a product, but order items and reservations restrict hard deletion. Order items can cascade from an order; transactions and reservations restrict it. Identity sessions and challenges cascade from a user, while orders and transactions keep the row and clear the association; linked reviews can restrict user deletion. These are schema observations. Direct user and order hard deletes, restore drills outside the disposable cluster, provider-side reconciliation, and a full process termination matrix at every commit boundary were not performed. The test named for crash recovery exercises an expired dispatch lease across worker instances.

Source-only risk: the administrator transaction deletion action calls a physical remove with no transaction-status guard in the service. PostgreSQL restricts deletion when a payment attempt references that transaction. Retention of cash or historical financial records without such a reference was not verified. Review the financial retention policy and add a preservation test before relying on that action.
