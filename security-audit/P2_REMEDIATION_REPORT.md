# Aljawhara.NET P2 remediation report

**Date:** 14 November 2026 (Asia/Damascus)  
**Disposition:** Local engineering review. No deployment, server configuration changes, or production or staging access.

| Finding | Original root cause | Changes |
| --- | --- | --- |
| AS-06 — Demo accounts | Startup seeded fixtures outside Production and Testing by default. Ten demo users shared a fixed credential. | The seeder exits before resolving persistence unless the host is Development and `DevelopmentFixtures:Enabled=true`. Each newly created demo principal receives an undisclosed credential with 256 random bits. Existing accounts and their credentials are retained. Synthetic addresses, orders and transactions are restricted to accounts created by that fixture run. Normal migrations, role initialization and separately configured non-production bootstrap remain independent of demo fixtures. |
| AS-07 — Spreadsheet injection | The transaction export interpolated text into CSV and returned the same bytes for Excel. | Both Admin export routes use the same existing filter, paging, ordering and eight-column projection. CSV uses UTF-8, CRLF records, quoted and escaped fields and invariant numeric/date formatting. Formula-capable text is prefixed with an apostrophe, including after ignorable leading characters. XLSX uses an Open XML workbook with explicit text cells, numeric amounts, typed dates and boolean refund flags. Amounts exceeding Excel's 15-digit precision are preserved as exact text; use CSV or decimal-aware tooling for totals that include those values. The invoice PDF download has no spreadsheet sink. |
| AS-08 — HTML email | Contact input and other displayed account and order inputs were inserted into HTML without encoding. The contact subject also went directly into the email subject. | All customer-controlled HTML fields are encoded. Contact line endings become template-owned line breaks after encoding. Verification links encode query parameters separately from the HTML attribute and require a configured HTTP(S) base URL. The contact recipient and MIME subject are fixed; the visitor's subject stays in the body. Email templates provide plain text and HTML alternatives. Contact has a 32 KiB request cap and a three-request, ten-minute limit per client IP per process. SMTP delivery has a timeout and a fakeable transport. |
| AS-10 — Review integrity | The original storefront route made persistent rating writes without authentication, verified ownership or a duplicate limit. | The unfinished local implementation and test already defined the storefront rule: an active, authenticated customer may submit one rating per active product after delivery of their own order containing that product as a live line item. This preserves the established local rule without adding a payment-status requirement. The existing Admin route may still submit reviews under its own authenticated Admin identity and shares the same per-product limit. Authors come from validated claims; request fields cannot supply an author. The database enforces reviewer identity and uniqueness. Ineligible storefront requests get 403, anonymous requests 401, and duplicates 409. The private “my rating” lookup is scoped to the caller. |
| AS-11 — Image uploads | Catalog multipart paths forwarded caller bytes, filename and MIME type to the public bucket. | Product, category and carousel create/update paths accept fully decoded JPEG, PNG and WebP. The decoder checks dimensions and frame count, requires successful pixel decode, applies image orientation and re-encodes pixels without forwarding original bytes or metadata. The server supplies names, suffixes and MIME values. Validation completes for the entire batch before any object write. Defaults: 8 MiB per source/result, 4096×4096 bounds, 12 million pixels, eight files, 32 MiB HTTP request and encoded batch cap. Configure `CatalogImages__MaxFileBytes`, `MaxWidth`, `MaxHeight`, `MaxPixels` and `MaxFiles` under the same configuration prefix. SVG, GIF, animated images and other formats are outside the allowlist. |
| AS-13 — Object deletion | Client-provided URLs went straight to R2 deletion after extracting a path, without product or bucket scoping. | Each requested URL must match a stored association on the route's product. Physical deletion requires this product's persisted owner UUID, the current account/bucket scope, the configured HTTPS asset origin and an exact generated product key. A stale image update cannot overwrite a changed image list. PostgreSQL commits removal first; any remaining catalog or order-item reference prevents physical deletion. Checkout takes the order's image snapshot under its stock reservation lock. Legacy, cross-owner, other-origin and uncertain objects are retained after unlinking; category and carousel updates/deletes also retain their underlying objects for reviewed cleanup. |

## Migration and compatibility

- `20261114083000_P2CatalogIntegrity` adds nullable `Products.ImageOwnerId` and `Ratings.ReviewerUserId`, a unique product owner index, a reviewer foreign key to Identity, and a partial unique index on product and non-null reviewer. The migration does not modify historical rows. Existing ratings, including legacy duplicate rows and aggregates, remain intact. For an account already listed as author of a legacy rating for the product, the API treats that review as fulfilling the one-review allowance. Older rows remain unattributed in the new column. Rollback drops the metadata and constraints, so it loses the ability to prove ownership of newer assets or enforce verified reviewer uniqueness.
- Storefront review requests must send the owned order ID alongside the existing product ID, content and score. Handle 401, 403 and 409. Public rating responses remain JSON with the existing properties and aggregation. Render review and catalog descriptions as text or through an approved sanitizer in the frontend.
- Both download URLs still work. Consumers that treated the Excel route as CSV must switch to an XLSX reader or the CSV route. The apostrophe is part of a risky CSV field's value and can appear in generic parsers. Prefer XLSX for normal spreadsheet use, and check the actual import workflow before relying on CSV; re-saving or importing through a tool that strips protective characters can change the interpretation.
- Presently deployed image URLs are unchanged. Where an upload fails between object storage and database commit, or deletion cannot be confirmed, orphaned objects may remain; there is no automatic janitor. The public asset hostname can change without renaming objects, but old URLs then unlink without physical deletion. Older app replicas do not enforce the new write rules; coordinate the cutover and migration.

## Local review of changed paths

- **Access control, IDOR and mass assignment:** catalog upload/delete and spreadsheet exports still require Admin. Storefront order and reviewer IDs are scoped to the principal. Catalog image owners and object keys are server assigned. Removal is an exact match against persisted links, and remote storage never derives a key from unchecked request input.
- **Stored XSS, encoding and input validation:** email MIME and XLSX types were inspected and CSV records were parsed independently. The raster decoder publishes fresh image bytes and derived media types. Rating and catalog JSON are not HTML; this does not prove that the storefront or Admin UI renders them safely. Existing legacy asset responses and actual bucket headers were not inspected. Desktop spreadsheet and mail client rendering were not verified by the parser and transport tests.
- **Business logic, race conditions and exposure:** PostgreSQL uniqueness settles concurrent ratings. Eligibility is checked at submission; later order status changes do not remove the rating. Catalog optimistic concurrency prevents stale image-list writes. Object cleanup is conservative if another entity references the same URL or persistence/storage is uncertain. End-to-end deletion is not atomic across PostgreSQL and R2. Contact IP throttling is process local and does not prevent distributed abuse. SMTP and storage failures do not expose raw provider messages through the changed routes. The P0 regression suite identified tracked SMTP and Telegram defaults reintroduced after the P1 report; those defaults were cleared and the forced enablement in Testing was removed without using or recording the credential values.
- **Dependencies:** The fresh NuGet audit identified two High severity advisories in the existing AutoMapper 16.2.0 dependency. Application now pins 16.3.0, the patched version identified by [GHSA-gpwp-5797-mjff](https://github.com/advisories/GHSA-gpwp-5797-mjff) and [GHSA-6vhm-j9h7-f9gh](https://github.com/advisories/GHSA-6vhm-j9h7-f9gh).

## Operator actions before deployment

1. Rotate and revoke any previously committed SMTP and Telegram credentials; verify historical JWT/API key retirement as called out in the P0 report. Identify already seeded demo accounts using verified provenance, then retire their credentials and sessions or remove them through an approved data process. The P2 migration does not guess account ownership by email and does not rewrite accounts.
2. Preflight migration up and rollback on a sanitized copy. Review locks, index creation, backups and database grants. Coordinate frontend review submission and error handling with the API update.
3. Bind `R2_PUBLIC_DOMAIN` to a dedicated HTTPS asset origin with no application cookies or executable content. Verify correct image Content-Type, `X-Content-Type-Options: nosniff`, and a restrictive document CSP such as `default-src 'none'; sandbox` on the asset origin. API headers do not apply to direct bucket downloads. Use a dedicated bucket/token with the minimum required access, disable development public aliases when appropriate, and review old objects for active content. The [R2 public bucket documentation](https://developers.cloudflare.com/r2/buckets/public-buckets/) distinguishes the development URL from a custom domain. Validate the native image decoder on the published Ubuntu runtime and keep it in dependency monitoring.
4. Review storage inventory and quarantine or clean up orphaned/legacy objects only after checking all references and retention needs. Verify trusted forwarded IP handling and set a cross-instance contact budget if needed. Confirm mail rendering, spreadsheet import behavior and storefront/Admin text rendering in an isolated release review. Keep the P1 merchant certification and refund restrictions in force.
