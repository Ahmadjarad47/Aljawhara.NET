# Aljawhara.NET security assessment

**Assessment date** 12 November 2026  
**Revision** `70ee24d` and the local working-tree changes present during review, including the Telegram integration and configuration changes.

The review identified **13 source-confirmed findings**, including three High findings. Credential material is present in application configuration, refresh sessions survive account security events, and the admin refund action records a refund without provider confirmation. The assessment also ran 61 existing defensive tests, including in-process HTTP tests against an isolated ASP.NET Core TestServer. These tests exercised existing controls. Runtime behavior of the new findings and deployment impact remain unverified.

See the [endpoint inventory](ENDPOINT_INVENTORY.md), [original test execution log](TEST_EXECUTION_LOG.md), and [remediation priorities](REMEDIATION_PRIORITY.md). The findings and source references below describe the original assessment; the current status is recorded here and in the [P1](P1_REMEDIATION_REPORT.md) and [P2](P2_REMEDIATION_REPORT.md) reports.

## 1. Confirmed vulnerabilities and security defects

The evidence in this section comes from the checked-out source or local Git objects. Verification describes the security invariant a future fix should satisfy with synthetic fixtures.

### AS-01 · High · Credentials in application configuration and Git history

- **Scope** API startup and outbound SMTP and Telegram. Historical signing configuration affects JWT-authenticated endpoints. CWE-798. OWASP A02 Cryptographic Failures and API8 Security Misconfiguration.
- **Evidence and impact** `appsettings.json` contains a non-placeholder SMTP password alongside a configured host and username. The password matches `HEAD`. The working tree also enables Telegram and contains a provider-shaped bot token absent from `HEAD`. Local Git history contains literal signing material and an API key field in historical snapshots. The application reads the SMTP password and binds the Telegram token from configuration. If any exposed value is active, someone with access to the checkout, history or copied configuration could misuse the associated service. Historical JWT signing material has elevated impact if any deployment still accepts it. The audit established the presence of the values and left their validity and rotation status unverified. [SMTP setting](../Ecom.API/appsettings.json#L46) · [Telegram setting](../Ecom.API/appsettings.json#L58) · [Telegram binding](../Ecom.API/Program.cs#L204) · [SMTP use](../Ecom.Application/Services/EmailService.cs#L713) · [Historical evidence](TEST_EXECUTION_LOG.md#credential-review)
- **Remediation and verification** Revoke and replace the current SMTP and Telegram credentials. Verify that historically exposed signing keys and API credentials have been retired. Inject replacements from the deployment secret store. Review relevant artifacts and history for copies. Verify that startup receives only injected credentials and that a local secret scan finds no credential literals in tracked configuration.

### AS-02 · High · Logout and account security events leave bearer sessions usable

- **Scope** `POST /api/Auth/logout`, `POST /api/Auth/refresh-token`, password change and reset, and `POST /api/admin/user-manager/users/block`. CWE-613 and CWE-362. OWASP A07 Identification and Authentication Failures and API2 Broken Authentication.
- **Evidence and impact** Logout returns success after logging, with no token mutation. Password changes and admin block update Identity state independently of refresh state. Refresh looks up a raw token and expiry, with no account lockout or email-confirmation condition. It issues credentials through a separate write and ignores the save result. JWT validation checks signature, issuer, audience and expiry. It has no account-state or session-revocation check. The actual JWT lifetime is 120 minutes, while the login and refresh response calculates expiry from configuration. A previously issued refresh credential can therefore continue a session after logout or block, and concurrent refreshes can yield responses inconsistent with the stored session. Database disclosure would expose usable refresh values until expiration or replacement. [Logout](../Ecom.Application/Services/UserManagerService.cs#L519) · [Block](../Ecom.Application/Services/UserManagerService.cs#L143) · [Refresh lookup and persistence](../Ecom.Application/Services/UserManagerService.cs#L823) · [Refresh issuance](../Ecom.API/Controllers/AuthController.cs#L489) · [JWT validation](../Ecom.API/Program.cs#L310) · [JWT lifetime](../Ecom.Application/Services/JwtService.cs#L58)
- **Remediation and verification** Store hashed refresh credentials per session. Redeem and rotate atomically and issue only after a successful write. Revoke sessions on logout, block and password changes. Enforce account or session validity for protected calls where immediate revocation is required, especially Admin APIs. Use one access-token expiration for the JWT and response. Defensive tests should assert revocation across each event, one successful redemption per refresh credential, and response expiry matching the token's actual expiration.

### AS-03 · Medium · Email verification and password recovery share an OTP namespace

- **Scope** `POST /api/Auth/verify`, `/resend-verification`, `/forgot-password`, `/reset-password`, and OTP issuance during registration and login. CWE-640 and CWE-307. OWASP A07 and API2 Broken Authentication.
- **Evidence and impact** Account verification and password recovery issue and consume codes through the same email-only cache key. Issuance overwrites an outstanding code regardless of purpose. The verifier uses separate read and remove operations and keeps no failed-attempt counter. Startup defines an `auth` limiter and maps controllers to the general `api` policy. The route scan found no binding of the `auth` policy. Login also issues another verification code for an unconfirmed account before password validation. Recovery accepts a code without proof it was issued for recovery. Shared state makes one flow interfere with the other and weakens the recovery boundary. [OTP issuance and consumption](../Ecom.Application/Services/OtpService.cs#L21) · [Verification](../Ecom.Application/Services/UserManagerService.cs#L356) · [Recovery](../Ecom.Application/Services/UserManagerService.cs#L454) · [Login ordering](../Ecom.Application/Services/UserManagerService.cs#L318) · [Rate policies](../Ecom.API/Program.cs#L363) · [Applied limiter](../Ecom.API/Program.cs#L523)
- **Remediation and verification** Bind challenges to a normalized account identifier and purpose. Use short expiry, atomic consumption and a per-challenge attempt budget. Apply separate issuance and verification throttles per account and per client. Verify purpose isolation, single redemption and a fixed attempt limit using an in-memory mail sink and synthetic accounts.

### AS-04 · Medium · Public coupon reads disclose user-assigned coupon data

- **Scope** `GET /api/Coupons`, `/active`, `/{id}`, `/code/{code}` and `POST /api/Coupons/validate`. CWE-862 and CWE-200. OWASP A01 Broken Access Control and API3 Broken Object Property Level Authorization.
- **Evidence and impact** Public reads return coupon codes and, in the full DTO, the assigned `AppUserId` and usage data. The active query filters date and status with no ownership condition. Public validation takes the caller's `UserId` from the body as eligibility context. These paths disclose private promotions and the internal identifiers associated with them. Checkout separately supplies the JWT-derived user ID and server-computed subtotal to coupon application, so the source evidence establishes disclosure and a weak validation boundary. [Public actions](../Ecom.API/Controllers/CouponsController.cs#L19) · [DTO and validation input](../Ecom.Application/DTOs/Coupon/CouponDto.cs#L7) · [Active query](../Ecom.Infrastructure/Repositories/CouponRepository.cs#L22) · [Eligibility check](../Ecom.Application/Services/CouponService.cs#L208) · [Checkout call](../Ecom.Application/Services/OrderService.cs#L184)
- **Remediation and verification** Provide a public DTO for unassigned promotions. Scope assigned coupon reads and validation to the caller or Admin. Derive validation identity from the authenticated principal. Test the expected visibility of public, assigned-to-self and assigned-to-another coupons and assert that public responses contain no user IDs or private codes.

### AS-05 · High · Refunds are recorded without a gateway refund

- **Scope** Admin-only `POST /api/admin/transaction/refund`. CWE-841. OWASP A04 Insecure Design. The API Top 10 has no direct category for the false provider-success condition.
- **Evidence and impact** The service checks that the transaction is paid and the amount is within the original payment. Its gateway helper waits and returns `true` without making a provider request. The service then persists the refund amount, date and flag and returns the updated transaction. A refund can appear completed in local records while the customer's funds remain with the merchant. Financial reports consume the local refund flag and amount. [Admin action](../Ecom.API/Controllers/AdminTransactionController.cs#L242) · [Refund persistence](../Ecom.Application/Services/TransactionService.cs#L549) · [Simulated gateway](../Ecom.Application/Services/TransactionService.cs#L897) · [Refund analytics](../Ecom.Application/Services/TransactionService.cs#L625)
- **Remediation and verification** Disable this operation until it is backed by verified provider evidence or an explicitly labeled manual reconciliation flow. Persist a distinct pending state and an idempotent refund identifier. With a fake provider, assert that timeout, rejection and duplicate delivery preserve accounting integrity and that only confirmed funds movement finalizes a refund.

### AS-06 · Low · Non-production seeding creates accounts with fixed credentials

- **Scope** Startup in environments such as Development or Staging and `POST /api/Auth/login`. CWE-1392 and CWE-798. OWASP A07 and API2 Broken Authentication.
- **Evidence and impact** `Testing` skips the seeder, and the seeder returns immediately in `Production`. Other environment names allow demo seeding by default. On a database with at most one existing user, it tries to create ten accounts from source literals, confirms their email state and assigns the `User` role on successful creation. Repository readers could know the credentials for those accounts in a shared non-production environment. The existing production guard passed an isolated defensive test. [Startup](../Ecom.API/Program.cs#L547) · [Production guard](../Ecom.Infrastructure/Data/DataSeeder.cs#L15) · [Demo user creation](../Ecom.Infrastructure/Data/DataSeeder.cs#L537) · [Test result](TEST_EXECUTION_LOG.md#executed-tests)
- **Remediation and verification** Keep demo data behind an explicit development fixture with generated credentials. Verify that default startup in every environment creates zero demo principals and that explicitly enabled development fixtures use unique generated credentials.

### AS-07 · Medium · Transaction exports write customer-controlled spreadsheet cells verbatim

- **Scope** Admin-only `GET /api/admin/transaction/export/csv` and `/export/excel`. CWE-1236. OWASP A03 Injection. No direct API Top 10 category for spreadsheet formula injection.
- **Evidence and impact** Checkout accepts a shipping full name. Transaction mapping takes the name from the associated shipping address. The CSV writer interpolates the name directly without CSV quoting or formula neutralization. The Excel export returns the same CSV bytes. This can corrupt column boundaries or cause a spreadsheet application to interpret customer data as a formula, depending on the operator's import settings. [Shipping input](../Ecom.Application/DTOs/Order/ShippingAddressDto.cs#L26) · [Transaction mapping](../Ecom.Application/Mappings/MappingProfile.cs#L173) · [Export implementation](../Ecom.Application/Services/TransactionService.cs#L808) · [Export actions](../Ecom.API/Controllers/AdminTransactionController.cs#L567)
- **Remediation and verification** Use a standards-compliant CSV writer and apply a policy for formula-capable cells. Generate a real workbook with explicit text cells if the Excel route is retained. Test stable column counts for names with punctuation and line breaks and assert text cell types for untrusted fields.

### AS-08 · Medium · Public contact input becomes HTML email markup

- **Scope** `POST /api/Auth/contact`. CWE-116. OWASP A03 Injection. No direct API Top 10 category for this HTML email sink.
- **Evidence and impact** The public controller passes contact fields to the mail service. Name, phone, subject and message are inserted into an HTML template without context encoding, and the result is assigned to the MIME HTML body. A sender can influence the HTML presentation of a message delivered to the configured operational workflow, including the placement of deceptive content. Mail-client behavior and delivery were unverified. [Controller](../Ecom.API/Controllers/AuthController.cs#L827) · [HTML template](../Ecom.Application/Services/EmailService.cs#L466) · [MIME body](../Ecom.Application/Services/EmailService.cs#L722)
- **Remediation and verification** Encode every untrusted field before inserting it into HTML. Include a text alternative and add contact-specific abuse limits. Use a test mail sink to assert that formatting stays fixed and contact text appears as literal text.

### AS-09 · Medium · Public payment triggers reveal invoice state and initiate provider verification

- **Scope** `GET /api/Orders/payment-callback` and `POST /api/Orders/webhook/sadad-paid`. CWE-200 and CWE-799. OWASP A01 and API4 Unrestricted Resource Consumption.
- **Evidence and impact** The callback accepts a provider invoice ID without owner authorization and returns distinct outcomes for unknown, paid, terminal and pending attempts. The anonymous webhook and callback both invoke verification using the non-throttled path. The verifier checks for a local attempt and holds a lease for an in-flight request, then releases the lease on a normal unpaid result. This exposes invoice-state information and permits repeated provider work for a known payable attempt. Paid transitions still depend on authenticated provider evidence and feature configuration. [Webhook](../Ecom.API/Controllers/OrdersController.cs#L264) · [Callback](../Ecom.API/Controllers/OrdersController.cs#L323) · [Verification and lease](../Ecom.Application/Payments/PaymentOrchestrationService.cs#L397)
- **Remediation and verification** Keep public callbacks opaque, require authenticated and replay-resistant provider delivery when supported, and queue or throttle verification per invoice. Provide detailed status through the existing owner-scoped endpoint. Assert that public responses reveal no invoice state and that the fake provider receives at most the intended number of checks per invoice window.

### AS-10 · Medium · Anonymous clients can create persistent ratings

- **Scope** `POST /api/Products/{id}/ratings`. CWE-306. OWASP A01 and API6 Unrestricted Access to Sensitive Business Flows.
- **Evidence and impact** The action checks product-ID agreement and model validity, then persists the rating. The controller applies no authentication to this action, and the service applies no ownership, purchase or duplicate check. Ratings feed public rating aggregates. Unauthenticated submissions can affect product reputation and the review feed. [Rating action](../Ecom.API/Controllers/ProductsController.cs#L132) · [Persistence](../Ecom.Application/Services/ProductService.cs#L391) · [Product aggregates](../Ecom.Application/Mappings/MappingProfile.cs#L27)
- **Remediation and verification** Define the intended review eligibility, require authenticated authorship, and enforce an appropriate uniqueness rule in the database. Verify that only eligible identities can write and that retries or concurrent requests cannot create extra review entries.

### AS-11 · Medium · Catalog uploads publish unvalidated bytes with the supplied media type

- **Scope** Admin product and carousel create/update actions and category `with-image` actions. CWE-434. OWASP A05 Security Misconfiguration and API8 Security Misconfiguration.
- **Evidence and impact** The shared R2 adapter checks that the file is nonempty, writes its bytes with the caller-supplied `ContentType` and returns a public URL. The callers reviewed do not verify image format before upload. An admin session can publish arbitrary content through an image upload path. Browser script impact depends on the object hostname and response headers. [Product form action](../Ecom.API/Controllers/AdminProductsController.cs#L137) · [Category form action](../Ecom.API/Controllers/AdminCategoriesController.cs#L65) · [Carousel form action](../Ecom.API/Controllers/AdminCarouselController.cs#L57) · [Object write](../Ecom.Infrastructure/Services/CloudflareR2Service.cs#L41)
- **Remediation and verification** Enforce an allowlist of decoded image formats, derive media type server-side, apply per-file limits and use an isolated asset origin. Use a fake storage adapter to verify that content with inconsistent metadata or a disallowed format never reaches object storage.

### AS-12 · Medium · Password reset removes the existing password before validating the replacement

- **Scope** `POST /api/Auth/reset-password`. CWE-841. OWASP A07 and API2 Broken Authentication.
- **Evidence and impact** After consuming the code, the service persists password removal through Identity and then calls `AddPasswordAsync`. It handles replacement failure after removal and has no encompassing transaction or compensating update. A rejected password or persistence failure can leave an account without a usable password. [Reset action](../Ecom.API/Controllers/AuthController.cs#L298) · [Password mutation order](../Ecom.Application/Services/UserManagerService.cs#L479)
- **Remediation and verification** Use Identity's password reset operation with a purpose-bound token. Invalidate sessions on success and preserve the original credential on failure. In a disposable Identity store, assert that validation failure and injected persistence failure both preserve the original password.

### AS-13 · Medium · Product image deletion is scoped to the bucket instead of the product

- **Scope** Admin-only `PUT /api/admin/products/{id}`. CWE-639. OWASP A01 and API1 Broken Object Level Authorization.
- **Evidence and impact** The service filters the product's saved URL list, then separately passes every URL in `ImagesToDelete` to storage. The R2 adapter extracts the path and issues a delete against the configured bucket without checking the URL host, allowed prefix or association to the product. The product action can affect objects outside the record it is updating if the storage credential can delete those keys. [Admin action](../Ecom.API/Controllers/AdminProductsController.cs#L157) · [Product deletion loop](../Ecom.Application/Services/ProductService.cs#L317) · [Object deletion](../Ecom.Infrastructure/Services/CloudflareR2Service.cs#L67)
- **Remediation and verification** Derive deletion keys from objects already attached to the product, verify prefix and asset ownership, and scope storage permissions. In a fake bucket fixture, assert that a product update can remove only objects linked to that product.

## 4. Tests not performed in the original assessment

P1 and P2 subsequently ran disposable PostgreSQL, real JWT, and mocked provider tests as described in their [P1](P1_REMEDIATION_REPORT.md) and [P2](P2_REMEDIATION_REPORT.md) reports. The following limits refer to the original assessment.

- Targeted vulnerability reproduction, bypass attempts, guessing, and active DAST scans were outside the execution scope of this review. The application was exercised through a mocked in-process HTTP fixture for monitoring and through focused defensive unit tests.
- No stand-alone API, real checkout, database-backed authentication flow, full JWT validation matrix or payment-provider verification ran. A disposable commerce database and complete integration isolation were unverified. No production, staging or third-party service received audit requests.
- The backend's default scheme reads bearer JWTs and the reviewed authentication routes pass tokens in JSON. Cookie authentication, HttpOnly, SameSite and browser CSRF behavior of a separate storefront remain unverified. The `AllowCredentials` CORS setting does not itself demonstrate cookie-based authentication.
- Current vulnerability advisories, browser rendering, actual bucket response headers, database grants, Redis and deployed proxy settings were unverified. No npm dependency graph, active Redis service configuration or deployable Nginx configuration was found in this checkout.
- Static tracing covered SQL construction, JSON parsing, redirect and outbound URL construction, file paths, object ownership, payment state, and input mapping.
