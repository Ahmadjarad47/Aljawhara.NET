## Fixed findings

| Finding | Root cause | Implemented fix and local verification |
| --- | --- | --- |
| AS-02 — Session security | One raw refresh value per user, non-atomic redemption, no revocation in bearer validation, and mismatched JWT and response lifetimes. | Each sign-in creates a PostgreSQL session with the SHA-256 hash of a random 256-bit refresh credential. One conditional write rotates the hash. Reuse is rejected without revoking the winning session. Every bearer request checks the session, Identity stamp, expiry and account status; Admin claims require current role membership. Logout revokes the current session. Password changes, resets and administrative blocks revoke all affected sessions. The configured JWT expiry and response share the same UTC instant, bounded by session expiry. Verified by cross-host refresh races, replay, expiry, legacy bearer rejection, logout, password events, block/unblock and live Admin demotion. |
| AS-03 — OTP and recovery | Shared email-keyed cache, race between verification and removal, no attempt or issuance controls, and email issuance before password validation. | Separate purpose records keyed by user ID. Six-digit codes expire in 10 minutes and use a purpose-derived HMAC bound to the account, normalized email and Identity security stamp. PostgreSQL enforces one issuance per minute, three per account and purpose per one-hour window, and five failures per code. Conditional writes make proof single use. Login does not send codes; forgot/resend acknowledge eligible and ineligible accounts uniformly. Auth-specific IP limits are attached to the routes: 20 login or 20 verification requests per five minutes, 10 issuance requests per five minutes, and 40 refresh requests per minute. Verified with synthetic accounts, an in-memory mail sink, concurrent confirmation and replay/attempt/budget tests. |
| AS-04 — Coupon authorization | Public endpoints serialized admin DTOs, and the eligibility request accepted an arbitrary user ID. | Storefront endpoints project a restricted DTO. Only active, eligible-for-listing, explicitly public unassigned promotions appear in public lists. Assigned codes are visible to their owner and through Admin management. Unlisted unassigned codes can still be applied by someone who supplies the code; the preview omits the coupon object. Storefront validation derives identity from the bearer principal. Checkout rechecks ownership and capacity when reserving usage, calculates the discount from stored rules and calculates the order amount from stored prices. Verified anonymously, as owner, as another user, as Admin, and against PostgreSQL reservation predicates. |
| AS-09 — Payment callbacks | Public responses exposed verification state; every valid trigger could start a remote check. | Both public endpoints return an empty HTTP 200 for well-formed triggers. One durable pending request slot per known payable invoice coalesces duplicates; unknown and terminal invoices create no work. A worker uses the existing verification lease and a one-minute public-trigger budget, measured from the last verification. Provider verification is limited to 45 seconds inside the two-minute lease. Trusted owner status checks and operator reconciliation retain their separate paths and share the lease. The existing authenticated GetById evidence checks, certification switches and transactional finalization still govern Paid. A stale lease owner cannot finalize. Verified with opaque HTTP responses, fake Sadad responses, concurrent workers, unpaid evidence and replay after payment. |
| AS-12 — Password reset integrity | The existing password was deleted and committed before Identity validated the replacement. | Customer and both Admin password replacement paths use Identity's `GeneratePasswordResetTokenAsync` and `ResetPasswordAsync`. The customer must first consume a recovery code. PostgreSQL wraps proof consumption, Identity update and session revocation in one transaction. Invalid replacement passwords leave the old password usable and require a new code. An injected PostgreSQL error during revocation rolled back the password write, challenge consumption and revocations; retry with the same proof then succeeded. Verified expiry and replay of the client-facing reset code. |

The repository's [Sadad public contract review](../docs/checkout-audit/SADAD_OFFICIAL_CONTRACT_REVIEW.md) records the GetById requirement, webhook HTTP 200 acknowledgment and the absence of a published webhook signature or source authentication scheme. No signature, shared header, allowlist or event ID was assumed. Public payloads never authorize payment. The live merchant contract and certification remain open; mock results are evidence about this application only.

## Migration and compatibility

- PostgreSQL migration `20261112093003_P1AccountAndPaymentSecurity` adds `AuthSessions` (unique refresh hash and user foreign key), `AccountChallenges` (composite key, purpose and budget constraints), `Coupons.IsPublic` (default false; assigned coupons cannot be public), and a nullable, indexed verification request timestamp on `PaymentAttempts`.
- The migration drops the old raw refresh-token columns. Existing access tokens have no session claim and will be rejected; old refresh tokens are not imported and old OTPs must be requested again. Plan a coordinated cutover and notify users of the one-time sign-in. Do not run pre-P1 and P1 API replicas concurrently against the migrated schema.
- Existing account and password records, orders, payment records, coupon ownership and usage data are preserved. Existing promotions remain valid by code subject to ownership, dates and usage limits; previously unassigned promotions are no longer automatically listed. An existing coupon flagged single-use can no longer be reserved after its first use. The prior-schema upgrade test verified preserved account and coupon values using synthetic rows. Rollback recreates empty legacy token columns and drops P1 session/challenge state, coupon visibility flags and queued trigger timestamps; it cannot recover old tokens.
- Login/refresh retain their response envelope. Storefront clients should serialize refresh calls, replace the refresh token after a success, and handle HTTP 401 by reauthenticating if they have no current token. Recovery email now provides the short-lived code directly. The callback is acknowledgment only; the frontend reads payment status using the existing owner or guest-authorized route. Public coupon previews ignore any legacy `userId` field.
- Access-token lifetime honors the configured value within 1–120 minutes. Session lifetime is fixed from sign-in, default seven days, configurable from 1–90 days. All API replicas must share the signing key and synchronize their clocks. Changing that key also invalidates outstanding account codes.

## Remaining risks and operator actions

1. Record P0 credential revocation and replacement evidence without including values; check historical signing and API key retirement, and reconcile legacy refunds separately. Restrict access to backups and logs that may still contain pre-P1 token or credential data.
2. Before a reviewed cutover, preflight the migration and backup on a sanitized copy, confirm database grants and plan a coordinated release and customer reauthentication. Confirm the storefront handles refresh races, recovery messages, opaque payment callbacks and restricted coupon DTOs. Have a promotion owner approve each existing code before setting `isPublic`.
3. Confirm Sadad's merchant-specific contract and certification separately. Keep the existing Paid and discount certification gates closed until that evidence is approved. Callback acknowledgment can precede provider verification; if a worker stops after claiming a queued trigger, the existing pending-invoice poll and protected status check remain recovery paths.
4. PostgreSQL is on the bearer authentication path; database failure prevents successful authentication. A request authorized before an account security event can still finish. IP rate limits are process-local; the account and invoice budgets are shared in PostgreSQL. Neutral responses reduce enumeration, but password and email delivery timing and duplicate usernames can still reveal information. Review proxy behavior and session table growth under load; schedule retention of expired/revoked session metadata after approving a retention policy.
